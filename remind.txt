NFPKSum 项目流程与当前修改记录

一、项目概况

项目路径：E:\code\NFPKSum

项目是一个 Java 17/Maven 排样项目，整体流程分为两个排样阶段：

1. 第一阶段：NFP 多边形组块
   目录：src/main/java/org/example/nfp/
   作用：读取原始物品多边形，使用 NFP（No-Fit Polygon，不重叠多边形）搜索两个物品或组合块的合法贴合位置，生成组合块。

2. 桥接阶段：NFP 组合块转 BeamSearch 输入
   文件：src/main/java/org/example/beamsearch/application/NFPToBeamSearchBridge.java
   作用：读取第一阶段输出，把每个组合块的真实成员点集合计算成外接矩形，生成第二阶段需要的板材文件和矩形工件文件，然后调用 LoadingTestRun。

3. 第二阶段：BeamSearch 矩形排样
   目录：src/main/java/org/example/beamsearch/
   作用：把每个组合块当作一个矩形工件，按照组合块的外接矩形在板材上进行排样。

4. 可视化阶段
   文件：src/main/java/org/example/visualizer/PackingResultVisualizer.java
   作用：读取第二阶段的矩形排样结果和 polygons.json，根据组合块 UID（UPI）还原组合块内部的真实成员多边形，并绘制 PNG 图片。

5. NFP 文本结果查看
   文件：src/main/java/org/example/nfp/visual/OutputDataVisualizer.java
   作用：读取第一阶段的文本输出并展示组合块信息，当前只使用 score2，不再使用旧评分字段。

主要数据目录如下：

- data/inputData：第一阶段输入 JSON，包含物品多边形、旋转约束和板材信息。
- data/NFPresult1：第一阶段 BatchBlockStitcher 的输出目录。
- data/materialData2 或其他 materialData 目录：桥接阶段生成的 material.csv 和 workpiece。
- data/packResult7 或其他 packResult 目录：第二阶段排样结果，包括 optimized.csv、polygons.json 等。
- data/visualization7 或其他 visualization 目录：可视化生成的 PNG。

项目使用 Java 17、Gson 和 JavaFX 依赖，构建配置在 pom.xml 中。当前仓库没有 Maven Wrapper。


二、第一阶段 NFP 组块流程

第一阶段入口主要是 BatchBlockStitcher.java。

1. 读取输入

BatchBlockStitcher.processDirectory(...) 扫描输入目录下的 JSON 文件。每个物品会被解析成 PolygonItem，读取的信息包括：

- id：物品 ID。
- BackFrontPriority：正反面或颜色优先级标志。
- centPt：中心点。
- points：原始多边形顶点，坐标单位为毫米。
- rotate：该物品允许的绝对旋转角度集合。
- smallItem：业务上的小件标志。

PolygonItem 构造时还会计算：

- area：多边形实际面积。
- boxArea：原始多边形外接矩形面积。
- areaRate：area / boxArea。

非 smallItem 且 areaRate 大于 RECTANGULAR_AREA_RATE（当前为 0.96）的物品会直接作为单独块保留，不进入第一阶段的主动拼接池。其他物品会先作为单件 Block 放入 activeBlocks，之后进入轮次式拼接。

2. 轮次式全量候选生成

当前策略由 stitchByExhaustiveRounds(...) 执行。每一轮都基于当前 activeBlocks 重新生成候选，而不是沿着输入顺序单一路径贪心拼接。

每轮的主要步骤是：

1) 遍历当前所有块，把能够作为主块的块作为 baseBlock。
2) 遍历当前所有单件块，把单件物品作为待吸收的 item。
3) 对每个 baseBlock 和单件 item 调用 tryAddItem(...)。
4) 收集本轮所有合法候选。
5) 按本轮拼接收益 score2 从高到低排序。
6) 依次选择最多 count 个候选。
7) 同一轮内，已经被某个候选使用的主块或单件物品不能再次使用。
8) 将选中的候选替换成新的组合块，未选中的块继续留在下一轮。
9) 如果本轮没有可选候选，结束拼接，剩余 activeBlocks 作为最终块输出。

默认每轮最多选择 5 个结果，即 DEFAULT_ROUND_RESULT_COUNT = 5。命令行第三个参数可以覆盖这个值。

同轮冲突规则：

- 一个当前块不能同时参与多个候选。
- 一个待吸收的单件物品不能同时参与多个候选。
- 例如 A-B 和 B-C 同时存在时，先按 score2 选择排序靠前的候选，B 被占用后，另一个候选自动舍弃。
- 当前实现只限制同一轮内不重复；下一轮会基于新生成的组合块继续搜索。

3. 主块和小矩形限制

smallItem 标志本身不能直接说明一个物品是不是矩形，因为输入中存在 smallItem=true 但实际为四角梯形等非矩形多边形的情况。

Geometry.isRectangle(...) 会：

- 删除共线冗余点。
- 要求剩余有效顶点数为 4。
- 要求面积非退化。
- 检查相邻边是否正交。

只有 smallItem=true 且 Geometry.isRectangle(...) 为 true 的单件，才会被视为 smallItem 矩形，不能作为主拼接块。

smallItem=true 但实际是梯形或其他非矩形多边形的物品，仍然可以作为主拼接块。

主拼接块还必须满足：

- 成员数小于 Block.MAX_MEMBER_COUNT，当前上限是 20。
- BackFrontPriority 与待拼接物品一致。
- 当前块与待拼接物品之间存在兼容的旋转关系。
- 当前组合块仍满足第二阶段板材尺寸限制。


三、Block、ItemPlacement 和几何字段关系

1. PolygonItem

PolygonItem 表示一个原始单件物品。它的 points 是输入多边形的原始局部坐标。它还保留物品允许的绝对旋转集合 rotate、业务属性和面积信息。

2. Block

Block 表示第一阶段输出的一个排样单元，可以是单件，也可以是多个物品组成的组合块。

Block 的主要字段：

- id：成员 ID 用加号连接。例如 A+B 表示由 A 和 B 组成的组合块。
- placements：Block.ItemPlacement 列表，按成员顺序保存块内每个物品的最终状态。
- combinedCoordinates：把所有 placements 中的 placedPoints 依次拼接成一个扁平点集合。
- outline：根据成员多边形 Union 结果得到的组合块轮廓，必要时回退到 combinedCoordinates 的凸包。
- areaSum：所有成员实际多边形面积之和。
- sourceBoxAreaSum：所有成员在所选旋转下的原始外接矩形面积之和。
- boxArea：combinedCoordinates 的整体外接矩形面积。
- score2：sourceBoxAreaSum - boxArea。
- rotate：当前组合块可以保留的绝对旋转角度集合。
- backFrontPriority：组合块成员的优先级。拼接要求所有成员优先级一致。

3. ItemPlacement

ItemPlacement 表示某一个 PolygonItem 在 Block 内的实际位置，主要字段如下：

- item：原始 PolygonItem 对象。
- selectedRelativeRotation：该物品在 NFP 拼接中选择的相对旋转角度。
- translation：该物品经过旋转和拼接后的平移量。
- placedPoints：该物品完成旋转、平移和块内归一化之后的真实顶点。
- sourceType：NFP 候选来自外边界、孔洞、内部环等来源的标识。
- candidateScore2：该成员进入当前组合块时对应的候选 score2。

4. combinedCoordinates 和 placedPoints

placedPoints 是每个成员自己的最终坐标，保留了第一阶段真实的旋转和平移关系。

combinedCoordinates 是所有成员 placedPoints 的扁平集合，主要用于：

- 计算组合块整体 bbox。
- 计算组合块 boxArea。
- 计算 score2。
- 在 outline 构造失败时生成凸包。
- 在桥接阶段修正第二阶段矩形尺寸。

combinedCoordinates 不是一个可以直接作为单个有序多边形轮廓绘制的路径，它只是所有成员点的集合。要还原成员形状，必须使用每个 ItemPlacement 的 placedPoints。


四、outline 的语义和已知问题

1. outline 的原始语义

outline 在第一阶段被设计成当前组合块的几何外轮廓。BatchBlockStitcher.tryAddItem(...) 会把 block.outline 传给 PolygonStitcher.findBestStitch(...)，作为下一次 NFP 计算中的固定几何输入。

因此，outline 不能简单删除，也不能在第一阶段 NFP 拼接时完全忽略。

2. outline 不能作为第二阶段尺寸的唯一来源

Block.buildOutline(...) 调用 PolygonStitcher.largestUnionBoundary(...)。

largestUnionBoundary(...) 对多个成员多边形做 Union 后，如果结果存在多条路径，只保留面积最大的单条路径。这会造成以下风险：

- 多个成员互不连通时，较小的连通分量可能被丢弃。
- Union 结果存在多个路径时，其他成员的范围可能不在保留路径中。
- outline 的 bbox 可能小于所有成员实际点集合的 bbox。
- 第一阶段继续 NFP 时仍使用这个 outline，因此它可能不是所有成员的完整包络。

已确认的错误案例：

- 案例目录：data/packResult5/Cabinet1
- 组合块：28239521053+28239531053
- 第一阶段文本：data/newOutputData10/Cabinet1.txt
- 该块 outline 的 X 范围约为 367.933 到 2132.933，宽度约为 1765。
- 所有成员拼接后的真实点集合扩展到约 2132.933，高度约为 1150.417。
- 原桥接代码只依据过小的 outline 矩形进行第二阶段排样，第二阶段可能认为两个组合块之间没有重叠。
- 可视化根据 UID 还原完整成员多边形后，出现真实多边形重叠。

对照组合块 28226561166+28253231166 的 outline 与所有成员点范围一致，说明该问题是条件性问题，并非每个组合块都会出现。

当前处理原则：

- 第一阶段 NFP 继续使用 outline，因为它是当前 NFP 几何操作所需的输入。
- 第二阶段矩形化不再把 outline 作为唯一数据源。
- 第二阶段优先汇总组合块内所有 items[].placedPoints，再计算整体 bbox。
- 只有旧输出没有 items 或 placedPoints 时，桥接代码才回退到 outline。


五、score2 评分和候选选择

当前项目只保留 score2，旧的 score1、score3、candidateScore1、candidateScore3、contactLength、unionTotalPerimeter、computeIntPathPerimeter、computePolygonPerimeter 均已删除或不再存在。

1. score2 定义

单次候选拼接的 score2 为：

    主块外接矩形面积
  + 待拼接物品旋转后外接矩形面积
  - 拼接后两者点集合的整体外接矩形面积

也就是：

    score2 = boxAArea + boxBArea - boxABArea

Block 的累计 score2 为：

    Block.score2 = 所有成员 sourceBoxAreaSum - 当前组合块 boxArea

score2 越大，表示把成员合并到同一个外接矩形中时，矩形面积收益越高。

2. 候选过滤

PolygonStitcher 会对允许的相对旋转角度逐一计算 NFP，并遍历：

- NFP 外边界。
- NFP holes/孔洞边界。
- innerLoops/内部闭环边界。
- 每条轮廓的顶点。
- 每条轮廓的中点。
- 长边上的额外密集采样点。

候选只有同时满足以下条件才可能成为 bestCandidate：

- score2 大于 SCORE_EPS。
- NFP 采样位置与固定多边形没有正面积重叠。
- 候选几何有效。

BatchBlockStitcher.tryAddItem(...) 还会继续检查：

- Block 与物品的优先级和旋转约束兼容。
- 选定相对角度后，Block 的有效绝对旋转集合不能为空。
- 新物品与 Block 内已有成员没有正面积重叠。
- 新 Block 的 score2 大于 SCORE_EPS。
- 新 Block 满足第二阶段尺寸限制。

3. 每轮排序

本轮候选按照以下顺序选择：

1) 当前轮候选 score2 降序。
2) score2 接近时，成员数较多的组合块优先。
3) 仍相同时，按组合块 id 排序，保证结果有确定性。

排序使用的是本轮这一次拼接产生的 score2，不使用历史累计 score2 代替当前收益。


六、旋转角度交集和相对角度遍历

1. PolygonItem.rotate

每个 PolygonItem 的 rotate 是绝对允许角度集合，例如 [0, 90]、[0, 180] 或其他角度。构造时会把角度归一化到 0 到 359 度，并去重排序。缺少有效角度时回退为 [0]。

2. Block.rotate

Block.fromSingle(...) 初始使用单件物品的 rotate。

Block.withAdditionalItem(...) 在增加新成员后，根据旧 Block.rotate 和新成员的允许角度，计算新的有效 Block.rotate。只有后续仍能找到共同合法方案的绝对角度会保留。

3. relativeRotationsFor(...)

对于 Block 的绝对旋转 blockRotation 和新物品的绝对旋转 itemRotation，相对旋转为：

    relativeRotation = itemRotation - blockRotation

结果会归一化到 0 到 359 度，并去重排序。

这个相对角度会传给 PolygonStitcher。PolygonStitcher 对每个允许的相对角度旋转待移动物品，分别计算完整 NFP，然后比较所有候选的 score2。

4. validRotationsAfter(...)

选定相对旋转后，检查：

    itemRotation = blockRotation + relativeRotation

如果这个 itemRotation 在新物品的允许绝对旋转集合中，则对应的 blockRotation 可以保留。

如果没有任何 blockRotation 满足条件，该候选被拒绝。

5. 第二阶段可旋转判断

第二阶段是矩形排样，只需要区分当前方向和交换长宽后的方向。因此：

- Block.rotate 包含 90 或 270，表示第二阶段允许交换长宽。
- 只包含 0、180 或其他不包含 90/270 的角度时，按不可旋转处理。
- 当前 BatchBlockStitcher、NFPToBeamSearchBridge、NFPBlockPacker 已统一使用“包含 90 或 270 即可旋转”的判断。


七、组合块尺寸限制

当前第一阶段使用以下限制：

1. MAX_PACKABLE_BLOCK_LENGTH = 2440.0

组合块整体 bbox 的长边不能超过 2440。这里的长边是 max(bbox.length, bbox.width)。超过该值的候选不保留。

2. MAX_FIXED_ORIENTATION_BLOCK_WIDTH = 1220.0

如果组合块在第二阶段不可旋转，则其当前方向的 bbox Y 向宽度不能超过 1220。这样可以避免一个长边虽然不超过 2440、但固定方向的 Y 向宽度超过板材短边的块进入第二阶段。

3. 可旋转块

如果 Block.rotate 包含 90 或 270，则第二阶段可以交换长宽。此时只需满足整体长边不超过 2440，旋转后的方向还需要由第二阶段实际矩形尺寸和板材约束确认。

4. 限制检查时机

- 当前块作为主块继续搜索前，会检查 fitsSecondStagePackingBounds(block)。
- 新候选生成后，也会检查 fitsSecondStagePackingBounds(nextBlock)。
- 这样可以避免继续扩展已经无法进入第二阶段板材的块。


八、桥接阶段：根据 placedPoints 矩形化

NFPToBeamSearchBridge.parseBlocks(...) 解析第一阶段文本中的：

- block id。
- BackFrontPriority。
- rotate。
- boxArea。
- outline。
- items 中每个成员的 originalPoints 和 placedPoints。

writeWorkpiece(...) 计算组合块尺寸时调用 blockPlacedPoints(...)：

1. 收集 block.items 中每个 ItemRecord 的 placedPoints。
2. 将所有成员的真实点放到一个集合中。
3. 计算 minX、minY、maxX、maxY。
4. 令 Length = maxX - minX。
5. 令 Width = maxY - minY。
6. 如果旧格式没有 items 或 placedPoints，才回退使用 outline。

这一步修复了“第一阶段成员实际范围比 outline 更大，但第二阶段只看到过小矩形”的问题。

NFPBlockPacker 中也同步使用相同逻辑：优先依据所有 ItemRecord.placedPoints 计算 bbox，旧格式才回退 outline。

桥接阶段生成的 workpiece 是逗号分隔格式：

    BatchNo,UPI,Qty,Color,Length,Width,IsSpecial,Rotatable

其中：

- BatchNo：案例名。
- UPI：组合块 UID，组合块通常是用加号连接的成员 ID。
- Qty：数量，当前每个组合块为 1。
- Color：由 BackFrontPriority 映射得到。
- Length、Width：使用毫米单位的组合块外接矩形尺寸。
- IsSpecial：当前普通组合块为 0。
- Rotatable：当前约定为 0 表示可旋转、1 表示不可旋转，具体由 ProblemLoader/Box 的既有解析约定执行。


九、BeamSearch 输入、单位和排样流程

1. 板材文件

桥接阶段生成 material.csv，例如：

    Color,Length,Width,Grain
    0,2440,1220,0

Length 和 Width 使用毫米单位。

2. workpiece 文件

workpiece 的 Length 和 Width 也使用毫米单位。LoadingTestRun 通过 ProblemLoader 读取后，会在 BeamSearch 数据结构中按 10 倍缩放。

3. BeamSearch 内部单位

BeamSearch 内部坐标使用毫米乘 10 的整数单位：

- Container.length、Container.width：乘 10 的整数。
- Box.size、Box.variation：乘 10 的整数。
- PlacedCuboid.x、y、length、width：乘 10 的整数。
- Space 和 BeamSearch 内部位置判断也使用该整数坐标系。

例如：

- 2440 mm 的板材长度在内部表示为 24400。
- 872 mm 的 X 坐标在内部表示为 8720。
- 1491 mm 的矩形长度在 workpiece 中是 1491.0，进入 BeamSearch 后按 10 倍参与计算。

4. 第二阶段排样

NFPToBeamSearchBridge 的主要流程是：

1) 读取第一阶段 txt。
2) 读取 inputData JSON 中的板材尺寸。
3) 读取每个组合块的所有 placedPoints，并计算组合块 bbox。
4) 生成 material.csv 和 workpiece。
5) 调用 LoadingTestRun.runWithImprove(...)。
6) LoadingTestRun 按 Color/BackFrontPriority 分组，为每组创建 Instance。
7) 每个组合块作为一个矩形 Box 进入 BeamSearch。
8) BeamSearch 搜索板材数量和矩形放置位置，并执行后续 ImproveSol 优化。
9) 输出 optimized.csv、statistics.csv、日志等结果。
10) 桥接阶段另外生成 polygons.json，保存组合块 outline 和各成员的真实 placedPoints。

NFPBlockPacker 是另一条较早的直接调用 BeamSearch 的入口，也会把 block 转成 Box 并按优先级分组。它和 NFPToBeamSearchBridge 使用相同的 placedPoints bbox 修正，但输出文件格式和默认目录可能不同，不能不加区分地混用两条流水线的输出。


十、可视化如何还原真实成员多边形

PackingResultVisualizer 读取：

1. polygons.json

每个 block 保存：

- upi：组合块 UID。
- outline：组合块轮廓。
- items：成员列表，每个成员包含 id 和多边形 points。

当前 bridge 写入 polygons.json 时，items[].points 使用第一阶段已经旋转、平移和归一化后的 placedPoints，而不是原始 points。

2. optimized.csv

LoadingTestRun 输出的 optimized.csv 保存每个矩形组合块在板材上的：

- BoardNo。
- Color。
- UPI。
- X、Y。
- R。
- L、W。

可视化程序根据 UPI 找到 polygons.json 中对应的组合块，再把组合块内部每个 item 的多边形绘制到第二阶段的矩形位置内。

3. 坐标变换

PackingResultVisualizer 当前按 LoadingTestRun 的输出格式处理：

- optimized.csv 的 X、Y 是内部 ×10 整数坐标，例如 8720 表示 872 mm。
- polygons.json 中的 placedPoints 是毫米坐标，绘制前乘以 10。
- L、W 在 optimized.csv 中是毫米数，计算 90 度旋转时会再乘以 10。

R=0 时：

    tx = X + px * 10
    ty = Y + py * 10

R=90 时，当前代码使用：

    tx = X + py * 10
    ty = Y + rawL * 10 - px * 10

其中 px、py 是 polygons.json 中的毫米坐标，rawL 是 CSV 中原矩形长度的毫米值。

如果找不到对应 polygons.json block 或 items 为空，程序会退回绘制矩形。

同一组合块内不同 item 使用不同颜色和深色边界线，以便看到组合块内部的成员边界。


十一、单位检查风险

当前已确认 LoadingTestRun 中存在单位混用风险，相关重叠检查尚未修复。

LoadingTestRun 中：

- p.x、p.y 是 BeamSearch 内部 ×10 整数坐标。
- p.length、p.width 是 BeamSearch 内部 ×10 整数尺寸。
- rawL = p.box.length、rawW = p.box.width，单位是毫米。

但当前 rectList 和边界检查部分直接把 p.x、p.y 与 rawL、rawW 相加或比较，类似：

    p.x + rawL
    p.y + rawW

这会把 ×10 坐标与毫米长度混合，可能导致：

- 边界检查判断失真。
- 矩形重叠检查漏报或误报。
- 某些实际重叠的矩形无法被当前检查发现。

后续修复时应统一为同一单位。推荐在重叠检查中全部使用 ×10 整数：

- 坐标使用 p.x、p.y。
- 当前方向尺寸使用 p.length、p.width，或先把 rawL/rawW 乘 10 并结合 R 重新计算。
- 两个矩形统一按 [x, y, x + widthAlongX, y + heightAlongY] 检查。

也可以全部转换为毫米，但必须同时把 p.x、p.y、p.length、p.width 除以 10。

此外，NFPBlockPacker.writePackResult(...) 是另一种输出格式：它把 PlacedCuboid 的 X/Y/L/W 除以 10 后写出。该输出与 LoadingTestRun 直接写出的 optimized.csv 不能混用，使用可视化程序前必须确认结果文件来自哪条入口。
